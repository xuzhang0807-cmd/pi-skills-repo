# Docker 检查与维护

来源与适配差异见 [ORIGIN.md](ORIGIN.md)。本技能不要求安装 ECC 或其他插件。

## 先读现有配置
识别真实 Compose 文件、项目名称、服务、网络和卷。区分开发和生产，区分宿主机与容器里的路径/端口。不要凭默认文件名操作另一个项目。

优先使用只读检查，并将占位服务名替换为实际值：
```bash
docker version
docker compose config --quiet
docker compose ps
docker compose logs --tail=100 <service>
docker stats --no-stream
docker system df
```
自定义 Compose 文件时沿用项目已有的 `-f` 与项目名参数。日志可能含敏感信息，分享前脱敏；避免打印完整渲染配置中的凭据。

## 检查维度
- **构建**：使用项目适配且仍受支持的基础镜像，优先明确版本/摘要；分层缓存依赖，多阶段构建按需采用；不要复制宿主机依赖或密钥进镜像。
- **运行权限**：尽可能非 root、最小能力、限制资源；不要无说明授予 privileged、挂载 Docker socket 或整个宿主目录。
- **网络**：容器间使用服务 DNS；容器内 localhost 是容器自己；数据库尽量不对公网映射端口。核对监听地址、网络成员、DNS、代理和健康检查。
- **数据**：先确认哪些路径持久化、卷属于哪个项目、备份是否能恢复。重建容器不等于重建卷，更不等于数据已经安全。
- **可用性**：检查真实健康端点、依赖是否就绪、退出码、重启计数、磁盘空间和日志增长。不要只看容器显示 Up。

## 修复顺序
先给证据和单一假设，再对单个服务做最小修改，验证后才扩大范围。重建前记录旧镜像与配置。更新后检查目标入口、数据完整性与依赖连接。

## 禁止默认行为
不执行 `docker compose down -v`、全局 prune、删除数据库目录或清空日志。用户确实要求清理时，先列出精确对象、影响和备份，再执行获授权的部分。
不要把单机 Compose 一概认定为不能用于生产，也不要声称 Linux 容器验证了原生 Windows/macOS 行为。

## 输出
用“发现 → 证据 → 建议/实际变更 → 验证 → 回滚”报告，不罗列无关的 Docker 知识。
