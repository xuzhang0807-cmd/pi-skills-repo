# 先找根因，再修复

来源与适配差异见 [ORIGIN.md](ORIGIN.md)。不需要 superpowers 插件命名空间。

## 1. 复现与取证
读取完整错误上下文、时间、调用栈和失败命令。记录期望行为与实际行为，建立最小复现；无法稳定复现时先收集条件，不宣称已经确定原因。
查看相关差异、依赖版本和环境变化。多层系统逐个检查边界：输入是什么、输出是什么、在哪一层首次不符合预期。诊断环境变量时只报告存在/缺失，不打印令牌或密码。
从报错位置沿调用链追踪坏值的来源；错误暴露处不一定是错误产生处。

## 2. 对比正常路径
寻找同项目内真实正常的实现或运行环境。列出正常与异常之间的差异：配置、状态、权限、网络、版本和调用顺序。阅读关键参考的完整上下文，不只复制一行“修复命令”。

## 3. 一次验证一个假设
写出“观察到 A，因此怀疑 B；用 C 验证”。一次只改变一个因素，使用可撤回的最小实验。失败后更新假设，不叠加多个未知补丁。
时间敏感问题等待实际就绪条件，不靠任意 sleep 掩盖竞争。缺乏证据时明确未知，不把相关性当因果。

## 4. 最小修复与回归
先建立能暴露缺陷的测试或可重复检查，再修复根因。检查同类入口是否需要验证，但不顺手做无关重构。
验证原始复现已解决，同时运行受影响测试与项目可承受的回归。涉及测试实现时可使用同场景的 `test-driven-development`；结束前使用 `verification-before-completion`。
连续多次修复失败时停止盲改，重新审视共享状态、架构和前提；不要用大规模重写掩盖诊断失败。

## 输出
根因结论及置信范围；支持结论的证据；修改文件；实际测试命令与结果；仍未排除的问题。环境不可访问时交付诊断计划，不假装已经修好。
